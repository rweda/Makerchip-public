Live Doc

Live Doc is a set of capabilities that use Visual Debug (VIZ) to animate documents (currently, PDF). Live Doc supports a no-copy use model so new value can be added while honoring the document author's copyright.

Concept

What it does

A \viz_js block calls this.global.pdf.extractToFabric(this, source, opts) to fetch a PDF page, parse its vector drawing operators, and build the figure's geometry as fabric.Path and fabric.Text objects inside the VIZ canvas. \viz_js code can assign attributes to these based on simulation data and can provide live overlays so a static diagram comes alive to reflect simulation behavior.

Use models

Supplemental course materials — Create companion visualizations that augment preexisting course materials. Animate a circuit diagram from a lecture slide or textbook page. Let AI generate illustrative stimulus.

Live design documentation — Bring existing design specs to life to accurately relate project documentation with actual design simulations.

VIZ development flow — Use your favorite drawing tools to seed your VIZ development. AI typically does well at connecting your static drawings with a hardware model.

Concept video creator — Thinking outside the box, this same flow can be used outside the world of hardware to explain processes and concepts. Draw a static illustration, and instruct Copilot to render a video using VIZ.

Copyright model

In consideration of authors' copyrights, Live Doc features support a clear separation between the referenced figure and the Live Doc simulation animation capabilities. Live Doc code may be written to contain no copy of the referenced figure. The browser fetches and parses the document content at runtime, holding it only within the browser context. The VIZ code may contain only a reference to the PDF (URL or view ID). This reference may provide explicit attribution. Additionally, extractToFabric attempts, by default, to draw the document's copyright notice below the figure (see build.notice). Further attribution Text in the VIZ code may be necessary. Simulation overlays encapsulated in the VIZ code (values, colors, annotations) may be original work, not copied expression. This may keep the use consistent with the accepted interpretation of fair use for programmatic reference.

While Live Doc features aim to assist in avoiding copyright infringement, the user is ultimately responsible for ensuring that their use of Live Doc features complies with copyright law. It is highly recommended to consult with legal counsel when using Live Doc with copyrighted content.

Using the Makerchip VS Code extension with Live Doc

The Makerchip VS Code/Cursor extension provides guidance for AI agents to author Live Docs. This is the primary authorship path.

Authoring a Live Doc using an LLM inherently shares PDF data with third-party LLMs, which the PDF's copyright terms may not permit. So the extension's tools give an agent only a PDF's document information (title, permissions, copyright notice), and capture no VIZ showing its content, until you tell the agent either that you may copy the PDF's content, or that your LLM provider neither retains nor trains on your chat (providers often have settings for both). Even then, they give and capture nothing from a PDF whose permissions deny copying. With only the latter answer, the agent is guided to save no captures to your files and build the overlay by reference, without copying content into your code.

While agents are given guidance to avoid copyright infringement, this guidance may be inadequate to ensure compliance.

Content Access and CORS

The browser's same-origin policy applies to PDF requests inside extractFigure. A PDF server that sends Access-Control-Allow-Origin: * (e.g. GitHub Pages, many CDNs) is fetched directly. For unknown cross-origin hosts, the IDE probes with a HEAD request and caches the result per origin for the session. If that probe fails or times out, it routes the PDF requests through the configured CORS proxy. Nothing needs to be added to an allowlist.

Large documents

Live Doc requests PDF data by byte range when the server supports it, rather than downloading the whole file. It disables pdf.js's background streaming and automatic prefetch, so extraction reads only the document structure and the data needed for the requested page.

Range loading requires Content-Length, Accept-Ranges: bytes, and an uncompressed response. For cross-origin requests, the server must also expose the range-related response headers to browser code, for example with Access-Control-Expose-Headers: Accept-Ranges, Content-Range, Content-Encoding. If the needed headers are unavailable, or the PDF is served compressed, pdf.js falls back to fetching the entire file.

The CORS proxy rejects a response whose declared Content-Length exceeds 64 MiB, returning an HTTP 413 rather than truncating it. Responses without a declared length are relayed in full. Direct requests have no proxy size ceiling.

Code Flow

This section describes how Live Doc works. The API Reference that follows is the field-level specification; everything named here is specified there.

Flow Overview

Live Doc is a feature of the VIZ system. A \viz_js block contains an init() and a render() method which, for Live Doc, typically do the following.

The init() function calls extractToFabric() to convert the PDF figure into the Fabric.js objects that will be animated. It performs an "extract" stage and a "build" stage:

  • extract
    • fetches the PDF
    • extracts and presents the specified page's vector drawing operators and text
    • selects from them the desired figure's elements
  • build
    • converts them to Fabric.js objects, inserted into a fabric.Group
    • names these objects for later reference

extractToFabric() returns the group immediately, empty, so init() can return it for rendering by the VIZ system without waiting for the PDF. The group is populated asynchronously.

The render() function updates the properties of these named objects based on simulation data relative to the currently active cycle.

Reference example

The following \viz_js block illustrates typical patterns using the gated D-latch figure from page 11 of latches.pdf. It uses the $din, $wen, and $qlat signals from d_latch.tlv: two values already printed in the PDF are updated, and a new value chip is attached to the WE wire. The chip's anchor comes from the wire geometry inspected while authoring.

\viz_js
   box: {width: 235, height: 135, fill: "#fff", strokeWidth: 0},
   init() {
      // Convert the PDF figure to a Fabric.js Group.
      // this.liveDocElements is populated after init() returns, containing
      // the named Group elements.
      const figure = this.global.pdf.extractToFabric(this, {
         url: "https://cs2461-2020.github.io/lectures/latches.pdf"
      }, {
         // the figure extraction parameters
         extract: {page: 11, clip: true, select: {mode: "region", rect: [188, 593, 397, 681]}},
         // the build parameters which name wire value labels
         build:   {labels: {d_val: 9, q_val: 3}},
      })
      // position the figure (left/top) in the box
      figure.set({left: 8, top: 22})

      // A new value chip on the WE wire, in figure coordinates. The figure arrives beneath it.
      this._weChip = new fabric.Text("", {
         left: 43, top: 12, fontSize: 8, originX: "center", originY: "center"
      })
      figure.add(this._weChip)

      // Status text, placed in the box (not the figure Group).
      const status = new fabric.Text("", {left: 4, top: 120, fontSize: 8, fill: "#1565c0"})
      // The chip is a child of figure; do not also return it as a sibling.
      return {figure, status}  // note that figure contains _weChip
   },
   render() {
      // render() also runs before the PDF arrives, when the elements are not yet set.
      const el = this.liveDocElements
      if (!el) return []
      const d = '$din'.asInt(), we = '$wen'.asInt(), q = '$qlat'.asInt()
      el.d_val.set({text: String(d), fill: d ? "#2e7d32" : "#777"})
      el.q_val.set({text: String(q), fill: q ? "#2e7d32" : "#777"})
      this._weChip.set({text: String(we), fill: we ? "#e65100" : "#777"})
      this.obj.status.set({text: we ? "TRANSPARENT (Q follows D)" : "HOLD (Q locked)"})
      return []
   }

Completion

The group shows "Loading PDF..." until the figure arrives. Then the named elements are assigned to this.liveDocElements (or the property named by build.elementsAs, for a second figure), which doubles as render()'s readiness test. If extraction fails, the group's text reports the failure and the error is logged.

Once the group is populated, one of two optional callbacks, build.onReady or build.onError, is invoked, though the common case does not require them, and the example does not include them. Live Doc then calls this.rerender() (see the VIZ API docs) to apply the current cycle's simulation values and repaint.

Addressing the document

A source is either a URL or a document already open in a PDF view.

Addressing by URL

A URL is fetched by the browser, so the same-origin policy applies and the server's page-range support decides how many bytes move; both are covered under Content Access and CORS and Large documents. Documents fetched this way are cached per URL, so recompiling the same design does not re-fetch.

Addressing by view

A view ({view: "mybook"}) names a PDF the reader already has open, which is the route for a document no URL can reach — a licensed copy of a textbook or a spec. For example, \viz_js code might convert the PDF in the "mybook" view with:

this.global.pdf.extractToFabric(this, {view: "mybook"}, {
   extract: {page: 342, select: {mode: "largest"}},
})

There is no guarantee that the identified view contains the intended PDF. To address this, an optional fingerprint can be provided — the PDF's own identifier — which turns a wrong document into an error instead of an overlay landing on the wrong place. See source.

The .tlv file may remain free of any copy of the figure: the source names a view, and the geometry is re-derived at runtime from whatever document the reader supplied.

What comes out: primitives and labels

Extraction returns two flat arrays, called pools: primitives, the vector geometry, and labels, the text. You address individual items by position in a pool, so it matters what counts as one item.

A primitive is, by default, a subpath — everything drawn from one move-to until the next, one pen-down stroke. It is deliberately not a whole PDF path, because a path is not necessarily a logical element. A PDF may emit numerous unrelated segments as one compound path, and drawing tools routinely do to batch same-styled strokes for efficiency. Live Doc may need to apply styling at a subpath granularity, e.g. to color one of many wires.

Sometimes, though, the path grouping can be meaningful. It might group a logic gate symbol, a meandering wire, etc. Flattening to subpaths risks losing that grouping information. To address this, each primitive records the path it came from, numbered by the pool position of that path's first primitive. Subpaths of one path share that path number, which makes the group addressable as a unit, and a path with a single primitive has path equal to its position. Treat a path as "drawn together", not "belongs together".

Two cases keep a whole path as a single primitive. A filled path is never split, because its rings subtract from each other to make holes and splitting would break that. And splitSubpaths: false is available to turn splitting off everywhere if preferred.

A label is one PDF text item. Kerning can split "CLK" into "C" and "LK", which can affect matching on label text.

Choosing the figure

The selection step identifies the elements of the desired figure from the page. The default does so by clustering: primitives whose bounding boxes lie within a few pixels of each other are joined, and the largest cluster wins. A diagram's parts are bridged by its own connectors, so the whole diagram forms one dense cluster while page rules and stray marks fall out as singletons. A frame would join the figures it surrounds, so it belongs to no cluster. A frame is a primitive covering 90% or more of the page, such as a background fill, or one whose removal (with any nested primitives each enclosing all the rest, such as a slide's border over its backdrop) leaves two or more multi-primitive parts lying wholly inside it, such as a slide around several figures. Anything else that joins figures together can be kept out of clustering with the ignore option.

It is typically important to use subpath granularity for clustering, as paths can contain disjointed subpaths with large bboxes. Grouped crop marks in opposite corners, for example, join the entire page as a single cluster.

Clustering is generally a starting point, used to determine the correct crop. It can omit output labels or figure titles sitting slightly apart from the diagram, which an explicit crop rectangle can catch. See select for details.

Coordinates

Three coordinate systems are in play. All are in pixels at scale 1, which are PDF points, with y pointing down:

System Origin Used for
Page Top-left of the page select's rect and at; ext.bbox
Figure Top-left of the selected figure, ext.bbox's corner Everything extraction returns, and the figure's Fabric objects
Box The \viz_js block's box Your init() objects; see the VIZ documentation

Figure coordinates are page coordinates minus the figure's corner. For a region crop, figure (0, 0) is the corner of the rect you wrote; for a cluster, it is the corner of the cluster's extent, and a label sitting just outside the cluster can have small negative coordinates.

Placing it on the canvas

The group returned by extractToFabric encapsulates the figure. Its children are in figure coordinates, and its own transform maps them into the box: by default, figure (0, 0) lands at box (0, 0). Place, scale, or rotate the figure with ordinary Fabric properties, at any time — in init(), in onReady once the figure's size is known, or in render():

figure.set({left: 8, top: 22})              // figure (0, 0) at box (8, 22)
figure.set({scaleX: 0.5, scaleY: 0.5})      // scales about figure (0, 0)

left/top are where figure (0, 0) lands. Leave the group's originX/originY, width and height alone; they are what makes that true.

Overlays that should travel with the figure are added to the group in figure coordinates — the numbers you read off primitive.bbox while authoring. Add them in init(): the figure's own objects are inserted beneath them when the extraction lands.

const chip = new fabric.Text("", {left: 43, top: 12, originX: "center", originY: "center"})
figure.add(chip)                            // WE wire in the reference example

Use Fabric's add or insertAt, not addWithUpdate, which re-derives a group's coordinate system from its contents. Take anchor coordinates from the midpoint of a wire's bounding box, not from a label's position: labels sit near their wires, not on them.

An object that should stay in box space instead — a legend beside the figure, say — is returned from init() as usual. onReady's fig(x, y) maps a figure coordinate to box coordinates through the group's current transform, for positioning it.

A backdrop is like an overlay, but inserted at the bottom once the group is populated and the figure's size is known:

onReady: ({group, ext}) => {
   group.insertAt(new fabric.Rect({left: -10, top: -10, fill: "#fff8e1",
      width: ext.figure.width + 20, height: ext.figure.height + 20}), 0)
}

onReady() is also a good place to scale the figure to fit box-coordinate bounds because the figure's size is then known.

onReady: ({group, ext}) => {
   // Place figure, left/top-justified within these bounds:
   const [bx, by, bw, bh] = [5, 20, 225, 110]
   const s = Math.min(bw / ext.figure.width, bh / ext.figure.height)
   group.set({scaleX: s, scaleY: s, left: bx, top: by})
}

Driving it from simulation

Animating the figure needs illustrative VCD trace data. Generating this requires a hardware model and stimulus. These could be provided in the same .tlv file(s) containing the VIZ code, run in Makerchip. Or they could come from any external tool flow, using any HDL, with VIZ code provided in a separate .tlv file, where .vcd and .tlv files are separately loaded into Makerchip for viewing.

The resulting visualization may contain named elements (sourced from the PDF, like D and Q in the reference example) and overlays (added explicitly by the VIZ code, like the WE chip). Both are available to render() for updating each cycle to reflect the trace data.

The authoring loop

When authoring a Live Doc (generally done by an agent), it is necessary to inspect the extracted PDF elements. For this, the extract stage performed by extractToFabric can be run in isolation, as can its build stage:

  • Extract: extractFigure(source, opts): performs fetch, parse, and select, returning a Promise<ExtractResult> containing primitives and labels as plain data.
  • Build: toFabric(fabric, ext, opts) builds that result into Fabric objects synchronously. For a faithful build, extract with forBuild: true, as extractToFabric does.

This separation enables inspection of the pools before deciding which elements to name and where to anchor overlays. renderFigure() shows the original to compare the build against.

The extract and build arguments passed to extractToFabric() become opts arguments of extractFigure() and toFabric(), listed above and called internally by extractToFabric().

Settle the selection first. Figure coordinates are relative to the selected figure, so changing select or clip moves the origin of every coordinate read so far, and can renumber the pools. Choose them first, reading page coordinates (ext.bbox gives the figure box; adding its corner converts any figure coordinate), then freeze them, and only then read anchor coordinates and pool indices.

For the D-latch reference example:

// ext.labels for page 11, region [188,593,397,681], clip: true:
//   1:"1"(s_bar)  2:"1"(q_bar out)  3:"0"(Q)  4:"1"(q_bar feedback)
//   5:"WE"  6:"D"  7:"Q"  8:"0"(r_bar)  9:"0"(D)

Those positions hold for the same PDF and the same extract options — and only those. They are positions in the returned arrays, so anything changing what is returned renumbers them, along with path numbers: select, ignore, clip, gap, splitSubpaths, and text for the label pool. For a frozen PDF and a finished call that never happens, which is what makes a bare index the cheapest and clearest way to name something.

When a bare index is not enough — a document that may see minor edits, or a name that should describe what it picks — a selector matches on content or position instead.

The authored .tlv file generally need not inspect the figure, so it will simply use extractToFabric(). Or, if copyright is not a concern, programmatic extraction is not a requirement. The VIZ code can redraw the diagram outright if desired, using Live Doc for authoring only. The role of Live Doc, in this case, is complete after authoring the VIZ code.

Functions

extractToFabric(ctx, source, opts)

→ fabric.Group — synchronously

The entry point for \viz_js. Returns the figure's layer group immediately, empty, and inserts the figure into it when the extraction lands. That is what init() needs: it must return the objects VIZ places and cannot wait for a fetch. See Placing it on the canvas for the group's coordinates.

Parameter Type Description
ctx object The \viz_js context — pass this
source source Identifies the document
opts.extract ExtractOptions Parameters that control extraction
opts.build BuildOptions Parameters that control building to Fabric.js

In addition to BuildOptions, opts.build provides two optional callbacks. onReady() is called once the figure has been inserted into the group, or onError() is called if extraction fails:

opts.build Called with
onReady {group, parts, elements, notice, fig, ext} — a BuildResult plus group, the copyright notice's fabric.Text (or null), fig(x, y) (figure → box coordinates, through the group's current transform) and the ExtractResult
onError the error

Related behavior is described in Completion.

extractFigure(source, opts)

→ Promise<ExtractResult>

Fetches the PDF (or reuses the cache), parses the page, selects the figure, and returns primitives and labels in figure coordinates. No Fabric involvement.

Parameter Type Description
source source Identifies the document
opts ExtractOptions The same options as extractToFabric's extract group, unnested

toFabric(fabric, ext, opts)

→ BuildResult

Builds an ExtractResult into Fabric objects, in figure coordinates, and resolves named elements. No group and no placement: the objects can go into any container, including a \viz_js box directly, where figure coordinates are then box coordinates. Synchronous.

Parameter Type Description
fabric object The per-canvas Fabric.js clone, available as this.getFabric() in \viz_js
ext ExtractResult From extractFigure
opts BuildOptions The same options as extractToFabric's build group, unnested

Call it once loadFonts(ext, opts) resolves: Fabric measures a font's characters on first use.

loadFonts(ext, opts)

→ Promise

Loads the fonts that ext's labels use, in the faces they use, given toFabric's opts (for fonts). extractToFabric calls it before building.

renderFigure(source, opts)

→ Promise<string>, a PNG data URL

Renders a page region as pdf.js draws it, on white, e.g. to compare a build with its original while authoring. opts: page (default 1), rect ([x0, y0, x1, y1], page coordinates, such as an ExtractResult's bbox; default the whole page) and scale (pixels per px, default 2). marks, an array of {bbox, text, color} (page coordinates; color default red), outlines boxes on the render, each tagged with its text: pool ids, say, while writing selectors.

loadPdfjs()

→ Promise<pdfjsLib>

Escape hatch returning the underlying pdf.js library, for rendering a page to a canvas, reading document metadata, and other uses outside this API.

URL sources are cached across compilations, keyed by URL.

view — naming an open PDF

The mnemonic is the view's tab label.

view Resolves to
"latches.pdf" that view, by exact name
"latch" the one open PDF whose name starts with it — a unique prefix, like an abbreviated git SHA
"" (or omitted, given a fingerprint) the sole open PDF view

An exact match always wins outright, so "book" means book even when book+2 is open. Prefix matching exists because a view's name is uniquified on collision (book, book+2), so the name a .tlv was authored against may not be the name it gets. Ambiguity is an error listing the candidates, never a guess.

fingerprint — verifying the document
Source The PDF's trailer /ID, exposed as fingerprints — [original, modified]; either value matches
Reading it fingerprints in extractFigure's result, during authoring
With view omitted or "" Selects whichever open PDF it is
With a view name Verifies that view, erroring on mismatch rather than overlaying a shifted layout

It matches a byte-identical publisher distribution for every reader, but not a per-purchaser watermarked copy. For example, {fingerprint: "..."} selects by document identity. The original identifier can be retained across revisions, so a matching fingerprint does not by itself guarantee unchanged geometry or pool indices.

ElementSelector

Identifies one item, or several, within a pool. A bare integer is a pool position: s_val: 6 ≡ s_val: {nth: 6}. The two pools are indexed independently — labels: {x: 6} is ext.labels[6], primitives: {y: 6} is ext.primitives[6]. A primitive's path is the position of its path's first primitive, so {path: 6, all: true} is ext.primitives[6] and any sibling subpaths that follow it.

An object selector has keys with two roles. Keys that narrow apply first and are AND-combined, leaving a set of candidates; the key that picks then chooses from those candidates.

primitives: { q_wire: {path: 16, near: [32, 48.8]} }
//                     ^^^^^^^^  narrows to the subpaths of the path starting at primitive 16
//                               ^^^^^^^^^^^^^^^^^^  picks the one nearest that point

Narrowing keys:

Key Pool Keeps
text: "..." labels Labels whose text is exactly this. A label is one PDF text item, not always a whole visible label, so check the pool before relying on a match
path: N primitives Primitives of the PDF path whose first primitive is at position N
path: {from, to} primitives Primitives of the PDF paths starting at positions from through to, inclusive. Either bound may be omitted. Unlike an nth range, it never cuts a path short

A narrowing key the pool does not carry matches nothing: text against primitives leaves no candidates.

Picking keys:

Key Picks
nth: N The Nth candidate in pool order (default 0)
nth: {from, to} Candidates from through to, inclusive, in pool order → array. Either bound may be omitted; positions past the end are dropped, not null
nth: [a, {from, to}, …] A list of the above, concatenated in the order given → array. An index past the end gives null
near: [x, y] The candidate nearest this point, measured to the candidate's bbox centre. In figure coordinates
all: true Every candidate, in pool order → array

Use one. Where more than one appears, all wins, then near, then nth. Narrowing keys alone still pick a single element, because nth defaults to 0: {text: "0"} is the first "0" label, not all of them.

Three forms give an array result rather than a single reference:

labels:     { in_vals: [2, 4, 8] },                                   // an array of selectors
labels:     { input_vals: [{text: "0", nth: 0}, {text: "1", nth: 1}] },  // ...of object selectors too
primitives: { gate_paths: {nth: [3, 4, 5, 7]} },                      // one selector, nth list
primitives: { states: {nth: {from: 3, to: 10}} },                    // ...range
primitives: { wires: {nth: [{from: 3, to: 10}, 14]} },                // ...or both
primitives: { bundle: {path: 16, all: true} },                        // all: true
primitives: { arc: {path: {from: 120, to: 164}, all: true} },         // ...of a path range

Iterate the result directly: this.liveDocElements.in_vals.forEach((t, i) => t.set({text: String(vals[i])})).

Arrays of selectors and nth lists preserve the order written; ranges and all: true are in pool order.

Nothing throws when a selector matches nothing. A single-element selector yields null, an unmatched index in an nth list yields null, and an empty range or all: true yields an empty array. A mistyped text, an nth past the end, or a narrowing key aimed at the wrong pool therefore surfaces in render() rather than at build time.

  bbox: [x0, y0, x1, y1],   // the figure box, page coordinates
  page: {width, height},    // the page's size
  meta,         // counts, below
}

A primitive record, in figure coordinates:

Field Type Description
id string "p0", "p1", … — the index, so it tracks pool position
d string SVG path data (M/L/C/Q/Z), ready for new fabric.Path
bbox [minX, minY, maxX, maxY]
path number The PDF path this came from, numbered by the position of its first primitive, so shared by its sibling subpaths

Style belongs to a PDF path, so it appears only on the first primitive of each path, ext.primitives[p.path]. A path's subpaths are always consecutive in the pool, whatever the selection. A single-subpath path, the common case, is one primitive carrying its own style.

Style fields are fabric.Path properties, named and valued as in Fabric, which toFabric spreads straight on: always fill and stroke ("" for none; rgba(...) when the PDF paints with partial opacity) and strokeWidth (0 when unstroked); and, only when they differ from Fabric's default, fillRule, strokeLineCap, strokeLineJoin, strokeMiterLimit, strokeDashArray and strokeDashOffset. Lengths are in px.

A label record is fabric.Text properties, in figure coordinates, plus id ("t0", "t1", …) and bbox (approximate, as for a primitive): text, left, top, fontSize (approximate), and angle when the text is rotated. With forBuild, it also has the PDF font's fontFamily, fontWeight and fontStyle (each omitted when "normal") and fill. fontFamily is a CSS font stack: the PDF's family; a web font with the same metrics (Arimo for Arial and Helvetica, Tinos for Times, Cousine for Courier, Carlito for Calibri, Caladea for Cambria), else of the same generic family; then the generic family. Fonts embedded without a family name (Type3, MSTT…) get only the generic family's web font, and normal weight and style. before gives the position of the first primitive painted over it if forBuild is set; omitted if no primitive is on top.

An image record covers a run of PDF images painted with no selected primitive or label between them (a brush stroke may be hundreds of strips). It has bbox in figure coordinates. With forBuild, it has before, indicating the position of the first primitive painted over it (primitives.length if none), and order, indicating how many labels with the same before are painted under it, omitted at 0. And, with imageData, it has bitmap, an ImageBitmap of its pixels, transparent where it paints nothing.

rights is what the document says of its copyright: copyDenied, whether its permissions deny copying; notice, its copyright notice (from its XMP dc:rights, else an Info Copyright entry, else the first notice-like line of text on its first, selected or last page), or null; and, where its XMP has them, usageTerms and webStatement (a URL). A detected notice is a best effort, not a determination of the document's terms.

meta:

Field Description
selectMode The mode that was used
clusterCount Clusters found, or null for region and all
droppedPrims Primitives discarded by the selection
clippedPrims Selected primitives subsequently discarded by clip (also counted in droppedPrims)
imageCount Raster images on the page, which are not extractable as vectors; those meeting the figure box are in images
totalPrims Vector primitives on the page, before selection
numPages Pages in the document

BuildResult

Field Type Description
parts Array The fabric.Paths for primitives, a fabric.Image for each image with a bitmap, and the fabric.Texts for labels, in paint order
elements `{name: fabric.Text \ fabric.Path \ Array}` The references named by labels and primitives, merged flat. Mutate them in render() with el.set({...}) — the repaint after render() is automatic
